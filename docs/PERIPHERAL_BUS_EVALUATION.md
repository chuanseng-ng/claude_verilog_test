# Peripheral Bus Evaluation — AXI4-Lite vs APB (pre-Phase-6)

**Status:** RECOMMENDATION — pending human sign-off (this PR is the decision + plan; migration module-PRs link back here).
**Date:** 2026-06-24 · Bead `claude_verilog_test-ahe`.
**Why now:** Phase 6 adds **6 more register peripherals** (GPIO/I2C/PWM/WDT/TRNG/AES-SHA) on this bus. Settle the peripheral-bus standard before scaling, or re-do them.

## 1. Question

The SoC control path is an AXI4-Lite ring (`axi_lite_interconnect.sv`) fed from the AXI4 crossbar via `axi4_to_axilite.sv`. Do the downstream peripherals actually need AXI4-Lite, or is a simpler APB bus sufficient?

## 2. Findings (evidence-based)

### The ring carries two different classes of slave
`soc_periph_map_pkg.sv` — 7 slaves @ 0x2000_1000–7FFF (4 KB each):

| Slave | Class | Bus need |
| ----- | ----- | -------- |
| **GPU ctrl** (0x…1000) | accelerator command/config | AXI4-Lite-native (anchors the ring) |
| **DMA ctrl** (0x…5000) | master config | AXI4-Lite (it's also an AXI4 master) |
| **PLL regs** (0x…7000) | config | simple register file |
| **UART / SPI / Timer / IRQ** (0x…2/3/4/6000) | **simple register peripherals** | **APB-class** |

### The 4 simple peripherals are APB-equivalent
All of `uart_controller`, `spi_controller`, `timer`, `interrupt_controller` instantiate `axi_lite_register_bank` and are plain memory-mapped register files. No outstanding-transaction depth >1, no burst, no pipelined/concurrent R+W exploited, no locked/atomic, responses always OKAY. (`axi_lite_register_bank.sv:21` = depth-1 write + depth-1 read; `axi_lite_interconnect.sv:13` = depth-1 per channel; AXI-Lite has no bursts.)

### Which AXI4-Lite features are genuinely used
| Feature | Used? | Note / APB cover |
| ------- | ----- | ---------------- |
| Multiple outstanding (>1) | **No** | depth-1 everywhere → APB single-transfer equivalent |
| Burst | **No** | the bridge serializes AXI4 bursts to single beats already |
| **Byte strobes (`wstrb`)** | **Yes** | partial-word writes (UART/SPI byte lanes) → **APB4 `pstrb`** covers this |
| Concurrent R/W channels | not exploited | single CPU master serializes; only matters for a future 2nd control master |
| DECERR (unmapped) | partial | generated by the interconnect, not the slaves → APB `pslverr` covers |
| ID, AxPROT/LOCK/CACHE/QOS, EXOKAY | **No** | tied off / bookkeeping only |

**The only real AXI-Lite feature the simple peripherals use is byte-strobe partial writes — covered by APB4 `pstrb`.**

## 3. Recommendation — hybrid: AXI-Lite fabric + APB peripheral subtree

**Adopt APB for the simple-register-peripheral subtree; keep AXI4-Lite for the accelerator/master ports.**

- Add one **`axil_to_apb` bridge** off the AXI-Lite ring feeding an **APB4 peripheral bus** (APB4 for `pstrb`).
- Move **UART / SPI / Timer / IRQ** — and all Phase 6 peripherals (GPIO/I2C/PWM/WDT/TRNG/AES-SHA) — onto that APB subtree behind an `apb_register_bank` (same register logic, APB ports).
- **Keep AXI4-Lite** for **GPU ctrl** and **DMA ctrl** (they are accelerators/masters, AXI-Lite-native — the reason the ring exists) and optionally **PLL**.

This is the textbook SoC topology (AXI/AXI-Lite fabric + masters, single AXI-Lite→APB bridge to a slow-peripheral APB tree). It is the right structure **before** Phase 6 drops in 6 APB-class peripherals, and it keeps AXI-Lite exactly where it is justified.

**Net:** APB is sufficient (indeed the better fit) for the simple peripherals; AXI4-Lite stays for GPU/DMA. Gains: simpler per-peripheral slave (no AW/W-decouple FSM), 1-cycle-faster reads (no bridge latch on that subtree), and Phase 6 peripherals become trivial APB drop-ins. Cost: one bridge + per-module bus-port swap + re-verify.

### Alternative considered — keep all AXI4-Lite
Defensible (cohesion, zero churn, peripherals already verified `soc_all` 82/82). Rejected as the primary recommendation because it makes every Phase 6 peripheral carry an AXI-Lite register-bank FSM for no functional benefit, and APB is the conventional fit for these slow register IPs.

## 4. Migration plan (if approved) — per-module PRs linked to this one

This PR is the **main/tracking PR**. Each step below is its **own PR**, linked back here (bead `claude_verilog_test-mdu` epic + sub-beads). Re-run `soc_all` (verification-orchestrator) after each.

1. **`apb4_register_bank.sv` + `axil_to_apb.sv` bridge** (new RTL + unit tests). PR-1.
2. **UART** → APB register bank (swap bus ports; keep FIFO/snoop logic). PR-2.
3. **SPI** → APB. PR-3.
4. **Timer** → APB. PR-4.
5. **Interrupt controller** → APB. PR-5.
6. **`soc_top` + `soc_periph_map_pkg`** — insert `axil_to_apb` on the ring, move the 4 (+PLL?) slaves onto the APB subtree, rewire. PR-6.
7. **Full `soc_all` regression** + (optional) a 1M-cycle SoC stress re-run. PR-7.

Each PR keeps AXI-Lite for GPU/DMA untouched. APB4 (`pstrb`) preserves the byte-strobe writes. Delegation: RTL → rtl-design-orchestrator; sims → verification-orchestrator.

## 5. Decision
GO / NO-GO on the hybrid migration is a human architectural call (this PR). If GO → the `mdu` migration epic's per-module PRs proceed; if NO-GO → close `ahe`/`mdu` with "keep AXI-Lite ring as-is," and Phase 6 peripherals stay AXI-Lite-native.
